# D3-18-02 最终裁决

基准日期：2026-11-25。任务：双边隐私与恶意 Agent 审计服务的研究空间复核（只读，无代码、无原型、无部署）。

## 裁决：**STOP**

**正式关闭 SealCall × PRISM 这条候选线。**理由命中任务包 STOP 标准的三条：①现有成熟方案已分别覆盖关键性质；②新增机制只是把成熟原语做机械组合；③实际部署价值不足（外包动机是模型/参考运营而非计算卸载，且模型判断质量存在密码学无法补齐的硬伤）。

**不是 NARROW**：不存在"一个明确未解决的组合问题，值得保留且区别于现有工作"。见 §3 逐项证成。

---

## 1. 一页裁决摘要

**用户上轮的重新定位是对的，且被原文证实**：SealCall 的外包价值不是"把昂贵计算转移给服务器"——本地明文评分 19 μs，加密评分 0.176 s，慢 9,263×（本轮复核 9,263.16×）`[原文+算术]`；作者逐字说明 "The service model is motivated by access to maintained audit knowledge and operations" `[原文, §4.4]`。因此焦点确实应转向参考数据的保密边界，而不是马上接 SNARK。

**但转向后的结论是关闭，不是立项**：
1. **参考数据泄露是已声明的信任边界**：§3.3 逐字承认 controller 可经任意基向量查询恢复参考坐标，"The present trust model permits this access within C"，并把对 C 的参考保护列为 "a separate goal" 且引用两个现成 output-restricted 协议 `[原文]`。这不是待补漏洞。
2. **双边隐私已是成熟领域**：GAZELLE（USENIX'18）、SANNS（USENIX'20）、SOTERIA（2020）均在 semi-honest / honest-but-curious 下同时保护两侧数据，且 SealCall 自己引用它们作为参考保护路线 `[原文]`。
3. **恶意服务计算完整性已有成熟原语**：PRISM（CCS'26）、Batch,Pack&Prove（ASIACRYPT'26）、CRYPTO'25 三篇顶会工作已把"可验证 CKKS/RNS-HE 计算"做成通用机制 `[摘要]`；正文仍 `[UNVERIFIED]` 但不改变"不是新问题"的判断。
4. **工具调用绑定已存在**：SealCall §3.4 与 MVP/D3-13 都已实现结果↔调用绑定 `[原文]`。
5. **唯一全表皆弱的两项——查询来源约束与版本真实性外部锚——是信任边界/认证问题**，D3-13 H4、D3-15 root authenticity 已多轮证明纯密码学不解决 `[推断，跨轮次]`。

**最终回答用户的核心问题**：**我们正在把通用安全计算的已有成果重新包装成 Agent 应用**，而不是发现了一个新的 Agent 安全问题。继续做下去的产物是"系统集成"，不是研究贡献。停止筛选这个候选，回到 Agent 执行可信性、数据访问控制等主线，不影响后续研究 AI Agent 安全。

## 2. 逐项回答任务包 Phase 5 的五个审查点

**① 是否只是 GAZELLE/SANNS 与 PRISM 的简单组合？——是。**
窄化问题拆开后正是：`用户输入隐私` ← SealCall/GAZELLE/SANNS 已解决；`服务商模型隐私` ← SANNS 完全、GAZELLE/SOTERIA 有限；`恶意服务计算完整性` ← PRISM/BatchPack 已提供；`调用绑定` ← SealCall §3.4/MVP 已解决。四项各有现成机制，新增的只是把它们接到同一条审计流水线上 `[推断，基于矩阵]`。任务包明确：机械组合 → STOP。

**② 是否需要新的 Agent 专用协议绑定？——不需要新密码学绑定；缺的是信任边界定义，而它不属于本候选。**
"查询来源约束"（服务如何判断请求来自合法 Agent 上下文）在七篇中全表皆弱。但在 SealCall 的 trusted-C 模型下，C 本就是可信放行方并已在 §3.4 检查结果↔请求，**S 无需独立知道来源**；若 C 不可信，则整个 SealCall 信任模型失效，问题转为 zk-MCP 的 prover=agent 场景（威胁模型相反，D3-18-01 已记），不是本候选的补丁 `[原文 + 推断]`。版本真实性外部锚同理：D3-13/D3-15 已证其属认证/信任基问题，非 HE/SNARK 可补 `[跨轮次推断]`。

**③ 是否存在真实部署需求？——本轮未检出；且价值结构本身削弱动机。**
检索未发现"专业维护参考数据的外部审计服务 + 恶意服务 + 双边隐私 + Agent 调用绑定"的真实生产部署 `[UNVERIFIED，未检出≠不存在]`。更关键：既然外包价值在"参考知识与运营"，而 SealCall 目标部署中 C 本就被信任可读参考（§3.3 permitted），则"对 C 隐藏参考"在目标场景里没有需求 `[原文 + 推断]`。若强行换部署目标追求双边隐私，则落入 GAZELLE/SANNS 已有领地。

**④ 是否能通过可行实验验证？——当前不可行，且不是因为工作量大。**
D3-18-01 的解除条件 1（取得 PRISM/BatchPack 正文/代码）本轮仍未满足（Cloudflare 拦截，两个独立 URL + archive 路径均失败）；解除条件 3（模型质量实质提升）未满足：purpose_scope F1=0.171、recipient_binding 0.455 且 §4.2 显示自选取的 scorer 既非最准也非最快（LR 全折 F1=0.913、快 4.1×）`[原文]`。在无正文、无代码、无模型质量支撑下设计实验，只能产出不可证伪的性能预测——明确禁止 `[推断]`。

**⑤ 是否有合理的性能预算？——无法建立，不应编造。**
SealCall 端到端 0.663 s 中约 0.487 s（73%）是 BGE 编码，只有 0.176 s（27%）是加密评分 `[原文+算术]`。在其上叠加 zkSNARK/vHE 的绝对 prover/verifier/proof 成本全部 `[UNVERIFIED]`；PRISM 摘要的相对倍数来自不同负载，不可移植 `[原文摘要 + 禁止推断]`。**不报告任何性能预测数字。**

## 4. 最终回答（任务包要求逐字回答的问题）

> **我们到底有没有一个值得投入的 Agent 安全问题，还是正在把通用安全计算的已有成果重新包装成 Agent 应用？**

答：**就本候选线而言，是后者。** 我们没有一个在此刻值得投入的新 Agent 安全问题。四项目标性质分别已有成熟覆盖，其中"双边隐私"和"恶意服务可验证计算"都是 2018–2026 年间被独立研究清楚的问题；把它们与 SealCall 已有的 call binding 拼在一起，产物是工程集成，不是新的安全性质或新原语。真正的开放项（查询来源认证、版本外部锚、模型判断质量）分别属于信任边界与模型层，密码学证明不解决——这与 D3-14、D3-15、D3-17、D3-18-01 的结论同构。

**因此正式关闭 SealCall × PRISM 候选线，不进入原型、不做最小实验、不追加架构拼装。**后续研究回到 Agent 执行可信性（D3-13 H4 的执行事件真实采集/远程证明绑定）与数据访问控制等主线；这些方向虽也开放，但不属于"通用安全计算已有成果的重新包装"。
