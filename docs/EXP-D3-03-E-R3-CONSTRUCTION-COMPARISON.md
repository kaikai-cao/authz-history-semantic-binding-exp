# EXP-D3-03-E-R3 — Phase 2: Alternative Construction Comparison

## 0. 本文定位

目标是回答：**在保持 E-R1/E-R2 相同授权状态语义与安全前提下，是否存在比全树扫描更高效的 ID 全局唯一性与撤销状态验证构造？**

本文是设计比较，**不是实现报告**。除候选 A（E-R1 冻结基线）外，B/C/D 均为候选设计，未经 Halo2 实测的不写为"已验证优化"。最小可行性实验见 Phase 4 与 `EXP-D3-03-E-R3-SUMMARY.md`。

必须保持的语义（不可放宽）：
1. Parent 撤销有效性：派生子授权时 Parent 在当前 RR 中无记录。
2. Grant ID 全局唯一：完整 F 字段 ID 不在 GR 任何非空叶重复。
3. Revoke 目标唯一：完整 F 字段 ID 不在 RR 任何非空叶重复。
4. 两事件顺序状态链：event1 输入 = event0 输出，不引入 host 代入。
5. 8 public instances 不变、事件数≤2、不碰 A/B/C/D/E 冻结实现。

## 1. 候选 A：全树扫描（E-R1 基线，不改）

**机制**：每事件提供 GR/RR 各 16 槽完整 preimage，电路重算叶子 Poseidon 与 depth-4 root，绑定当前输入根；对每个非空叶比较完整 ID。

**优点**：语义清楚、易审计；不依赖 canonical slot 规则；已通过 mock 18/18、真实 proof、224 全量测试。

**成本**：505 Poseidon permutations（扫描 344，68.1%）、43 约束多项式、39 advice、K=15、8160 B proof、GR prove 中位 35016 ms。

**trust**：S0 唯一性为前置（方案 A，E-R2 已固化）；`key_field` 映射单射性外部信任。

**定位**：安全语义基准，本轮不动。

## 2. 候选 B：Poseidon Canonical Slot

**机制**：用完整 ID 的 Poseidon 派生规范槽位 `slot = H(id) mod 16`，冲突时线性探测；电路证明插入/查询走的是规范探测路径。

必须回答的问题（逐项）：

| 问题 | 分析 |
| --- | --- |
| 两个不同 ID 冲突如何不覆盖？ | 需电路内线性探测：从 `H(id)` 起逐个检查槽位，遇占用则前进。必须约束每个被跳过槽在探测时刻确实非空，且落点槽为空或同 ID。 |
| 如何证明没跳过更早空槽？ | 这是 B 的核心难点。必须对 `H(id)..target` 区间每个槽做非空断言，等价于该区间的局部扫描；最坏仍 16 槽。需保证探测顺序单调。 |
| 树满如何处理？ | 需电路约束"存在空槽"的析取，通常仍需扫描全部 16 槽或引入计数器证明。 |
| 与 D3-01 `D3-SLOT-v1` 兼容？ | **不直接兼容**。D3-01 用 SHA-256 对 32B id 取低 64 位 + 排序线性探测（`docs/d3_02_r1_canonical_slots.md:19,140`）；E-R1 用 Pallas Base F 字段 ID + Poseidon。SHA-256 在 Halo2 内昂贵且当前电路无 SHA-256 gadget。 |
| 是否引入新版本？ | 若改用 Poseidon 派生槽位，需定义新 layout version（`D3-SLOT-v2` 之类），牵涉状态迁移与固定向量版本化。本轮冻结边界不允许。 |
| host 算 slot 可信吗？ | **不可信**。若仅由 host 提供 slot 而不在电路证明 `slot=H(id)` 与探测完整性，则退化为 E-R1 已修复的"witness 指定槽位"漏洞。 |

**结论**：B 在"证明探测完整性"上等价于局部全树扫描，且引入 SHA-256→Poseidon 槽位规则版本冲突与设计空间扩大。**理论可行但成本收益不明确，且触及冻结布局版本；本轮不实现。**

## 3. 候选 C：独立 ID 索引树（重点候选）

**机制**：在 GR/RR 状态树之外，维护专门的 ID 索引承诺（如按 ID 键的 membership 树/累加器）。把三类检查转化为索引树上的局部非成员/成员证明：
- Grant 唯一：新 ID 在 GR-ID 索引中 non-membership。
- Revoke 唯一：新 ID 在 RR-ID 索引中 non-membership。
- Parent 有效：Parent ID 在 RR-ID 索引中 non-membership（未撤销）。

**关键分析维度：**

| 维度 | 分析 |
| --- | --- |
| 新增状态根 | 需要 GR-ID 与 RR-ID 两个索引根（或合并），当前 8 instances 没有空位；必须新增 instance 或把索引根绑定进现有承诺，触及 public instance 冻结。**这是 C 的最大兼容障碍。** |
| 更新约束 | 每次 Grant/Revoke 需同步更新主树 + 索引树两套承诺，需证明两者一致（同一 ID 同时插入/标记）。 |
| 初始状态可信性 | S0 索引根同样需可信锚定；与 E-R2 方案 A 一致，但多一套不变量。 |
| 局部非成员成本 | 若索引树按 ID 排序或哈希分桶，非成员证明可用单个 opening + 相邻/空位证明，理论远小于 16 槽扫描。 |
| 与现有 8 instances | 不兼容除非重新定义承诺封装；本轮冻结不允许改。 |

**结论**：C 在理论上最有希望把 O(16) 扫描降为 O(log n) 局部证明（这也是用户判断的方向），但**需要新增状态根与 public instance**，超出本轮冻结边界。可作为独立优化原型阶段评估，本轮只做 host 层最小实验（Phase 4），不接入电路。

## 4. 候选 D：排序 ID 集合

**机制**：维护按 ID 升序排列的状态集合；插入新 ID 时证明其前驱 < 新 ID < 后继（或落在空位），用相邻元素关系证明不存在。

**关键分析维度：**

| 维度 | 分析 |
| --- | --- |
| 排序维护成本 | 有序插入需移动后续元素，固定 16 槽下最坏 O(16) 写；电路内需约束全序与移动正确性。 |
| 插入更新 | 需证明新 ID 严格位于前驱/后继之间，且 prior/next 是真正相邻（无跳过的元素）——仍需对中间槽做空/占用断言。 |
| 撤销状态 | 撤销需从 GR 有序集删除或在 RR 有序集插入，两套顺序一致性约束复杂。 |
| 固定容量 | 16 槽满时需额外处理；与树满问题同源。 |
| Halo2 难度 | 排序网络/比较器在 F 字段上可行（`assign_pair_u64` 已有位级比较），但全序维护的动态移动在固定 region 布局下复杂。 |

**结论**：D 最坏情况仍可能退回 O(16) 扫描（证明无跳过），且撤销/双集合一致性复杂。**理论可行但成本收益不明确，本轮不实现。**

## 6. 共同诚实边界

- 所有候选的"局部证明"是否真的比 344 permutations 便宜，**未经 Halo2 实测即不成立**。
- B/C/D 不削弱语义的前提是"完整 ID 比较 + 探测/非成员证明在电路内可验证"；若退化为 host 断言则是 E-R1 已修复的漏洞。
- 8 public instances、事件数≤2、A/B/C/D/E 冻结为本轮硬约束；任何需要新增 instance 或改布局的候选只能进入独立原型阶段，不能写成本轮成果。
