# EXP-D3-07-B-P2 — 崩溃与持久化分析（Crash Analysis）

> 设计审计产物，不含实现。基线 `exp-d3-07-b-p1-r1-c1` @ `2b84300`。
> 本文件逐项分析任务包要求的八类崩溃位置，给出重启后状态、是否可继续签名、是否可能双签、
> 是否需要人工恢复、以及对安全性/活性的影响。
> **重要**：本设计只提出持久化状态与写入顺序的**要求**，不声称任何已实现的存储是 crash-safe。

## 0. 关于"crash-safe durable storage"的前置声明

任务包特别指出：不能把内存字典、JSON 导出或普通文件写入直接描述为 crash-safe durable storage。本节遵守该约束：

- 本文用**抽象原语**描述需求：`durable_write(x)` 表示"写入后即使进程崩溃，重启也能读到写入前或写入后的完整值，不会读到撕裂值"；`atomic_write_two(a,b)` 表示"a、b 要么都生效要么都不生效"。
- 实现类选项（不在本轮范围、不声称已具备）：带 fsync 的追加日志 + 校验和、WAL、数据库事务、带幂等键的复制存储。这些只是**候选机制**，本设计不验证其 crash-safety。
- 崩溃一致性结论是**在 `durable_write`/`atomic_write_two` 原语成立的前提下**推导的；原语若不成立，结论作废。
- P1 模拟器里的"持久化"只是 Python 字典状态的 dump/restore，**不是** crash-safe 证据；R1-C1 明确不声称生产级持久化。

记三个受保护对象：
- `L = (locked_round, locked_digest)` —— `durable_lock`
- `P = pending_vote`
- `S = signed_votes` 日志

写入纪律（设计目标）：签名前先 `durable_write(P)`；precommit 返回签名前 `atomic_write_two(L, S)`；解锁改签必须把新 L 与新 S 条目在同一恢复单元内落地。

## 1. 崩溃位置逐项分析

### 崩溃 1：写入 pending lock（`P`）之前崩溃

- **重启后状态**：无 `P`、无新签名、`L` 保持旧值、`S` 不含该票。
- **是否允许继续签名**：允许——Witness 视作"尚未开始该次签名"，可重新走完整 `can_sign`。
- **是否可能双签**：否。未产生签名，S1 不受影响。
- **是否需人工恢复**：否。
- **安全/活性影响**：安全无影响；活性可能损失一次签名机会，可重试。证据标签：由规则推导；P1 未建模崩溃点，故**未被 P1 模拟器覆盖**。

### 崩溃 2：pending lock 写入后、签名前崩溃

- **重启后状态**：`P` 存在（已签名准备），`S` 无该票，`L` 旧值。
- **是否允许继续签名**：允许，但必须先重新验证 `P` 对应的提案仍满足 §2 前置（轮次、锁、PoLC）；若条件已变（如已锁定冲突 digest），必须丢弃 `P` 并拒绝。不得"凭 pending 就直接签"。
- **是否可能双签**：否，前提是重启后重新执行 `can_sign` 且 `current_round` 未被签名请求抬高（R1-C1）。
- **是否需人工恢复**：否。
- **安全/活性影响**：pending 残留可能造成短暂阻塞，但 timeout 可推进轮次绕开； Model A 下这类残留会永久阻塞（P1 的 P1-A），Model B 下由 PoLC 解锁路径处理。证据标签：由规则推导，未被 P1 崩溃建模覆盖。

### 崩溃 3：签名完成后、发送前崩溃

- **重启后状态**：`S` 含该票（假设签名与日志原子落地），`P` 可清除，票未广播。
- **是否允许继续签名**：该票已签，不得对同轮同 `lock_key` 的另一 digest 再签（S1）；可重广播已签票。
- **是否可能双签**：否——已签事实由 `S` 约束；这正是 `S` 必须持久化的理由（S5）。若 `S` 丢失则回到崩溃 8 的情形。
- **是否需人工恢复**：否（若 `S` 完整）。
- **安全/活性影响**：安全由 `S` 保持；活性上该票未被他人观察，可能延迟 PoLC/QC 形成，但可重广播。证据标签：由规则推导 + P1 的 S5 重启语义支撑（非崩溃点模拟）。

### 崩溃 4：发送后、记录投票日志前崩溃

- **重启后状态**：票已广播给他人，`S` **可能不含**该票（取决于日志先后）。
- **是否允许继续签名**：危险点。若 `S` 缺该票而本 Witness 仍处同轮同 `lock_key`，可能对该轮另一 digest 再签，形成事实双签。
- **是否可能双签**：**可能**，若发送先于持久化日志且无其他约束。
- **缓解要求（设计规则）**：把"追加 `S`"放在"广播"之前（签名 → 写 `S` → 广播），使发送后崩溃时 `S` 已有记录；重启后按 `S` 判定已签事实。
- **是否需人工恢复**：若日志确实丢失且他人持有该签名证据，需外部证据重建；本设计不自动解决。
- **安全/活性影响**：这是最危险的写入顺序。安全依赖于"日志先于发送"。证据标签：由规则推导；P1 把 `signed_votes` 视为即时可读，未模拟此窗口，故**未被 P1 覆盖**。

### 崩溃 5：precommit 锁写入后、签名返回前崩溃

- **重启后状态**：`L=(r,digest)` 已更新（若 `atomic_write_two(L,S)` 生效），`S` 含对应 precommit；签名尚未返回给调用者。
- **是否允许继续签名**：锁已生效，本轮不得改签冲突 digest；可重发已写 precommit。
- **是否可能双签**：否，前提是 `L` 与 `S` 原子落地；若只写了 `L` 未写 `S`，重启后仍由 `L` 约束解锁规则，不会自动双签。
- **是否需人工恢复**：否（原语成立时）。
- **安全/活性影响**：安全由 `L` 保持；活性上签名返回值丢失可由重发补偿。证据标签：由规则推导 + P1 的 R1-B7（锁完整恢复）支撑，但非真实崩溃模拟。

### 崩溃 6：完整重启

- **重启后状态**：按 P1 的 `restart()` 语义：full / lost_pending 保留 `locked_round/locked_digest`，lost_all 归零；本设计要求至少保留 `L` 与 `S`。
- **是否允许继续签名**：允许，但 `current_round` 重置后必须重新通过显式 `ROUND_ADVANCE` 进入目标轮次；签名请求不得隐式抬高（R1-C1）。
- **是否可能双签**：否，若 `L` 与 `S` 完整恢复（P5/P6/R1-B7 通过）。
- **是否需人工恢复**：否（若持久化完整）。
- **安全/活性影响**：P1 的 P5/P6 通过；安全保持。注意 `current_round` 归零不得否定 `L`——这是两个独立状态。证据标签：已由 P1 模拟器验证（P5/P6/R1-B7），但持久化本身仍是外部假设。

### 崩溃 7：pending 状态丢失（签名日志仍在）

- **重启后状态**：`P` 丢失，`S` 仍在。
- **是否允许继续签名**：可从 `S` 重建"该票已签"事实，据此拒绝同轮冲突签名；对未完成部分重新走 `can_sign`。
- **是否可能双签**：否，只要以 `S` 为准判定已签事实。
- **是否需人工恢复**：否。
- **安全/活性影响**：P1 的 S5/P5/P6 在此情形通过（"pending 记录丢失但 signed_vote 日志仍在"）。证据标签：已由 P1 模拟器验证；但 `S` 的可恢复性仍是外部假设。

### 崩溃 8：全部本地状态丢失（pending + 签名日志 + 锁皆失）

- **重启后状态**：本地无锁、无签名证据；Witness 无法证明自己曾签过什么。
- **是否允许继续签名**：本设计规定——**不得**仅凭本地空状态就自由签名；必须先从可信来源（其他 Witness 的投票证据、Gateway 的 committed 记录、外部恢复流程）重建状态。在此之前 fail-closed 拒绝签名。
- **是否可能双签**：**可能**，若节点带着空状态重新加入并自由签名，可能与自己过去的签名冲突；本地无法检测。
- **是否需人工恢复**：**是**（外部恢复/重新配置）。
- **安全/活性影响**：P1 的 AL1 显示此情形下 S5 失败；"持久化锁可信"是外部假设。安全依赖外部证据重建，活性需要管理员介入。证据标签：已由 P1 模拟器验证其失败（AL1）；恢复机制本设计不定义，属未解决问题。

## 3. 需要原子持久化的状态对

- `precommit`：`atomic_write_two(L, S_entry)` —— 防止"锁写入但签名证据丢失"或反之产生的不一致视图。
- `解锁改签`：新 `L` 与解锁依据 PoLC、新 `S_entry` 在同一恢复单元；避免"锁已清但新锁未写"窗口（§3.5 of STATE-MACHINE）。
- `pending`：`durable_write(P)` 先于签名，签名后 `durable_write(S_entry)` 先于广播（针对崩溃 4）。

## 4. 明确不声明

- 未验证任何具体存储实现满足 `durable_write`/`atomic_write_two`；8 类中 1–5 的崩溃点在 P1 模拟器中未被建模，结论是规则推导而非模拟验证。
- 崩溃 8 的恢复机制、quorum 重建流程未定义。
- 本分析不是 crash-safe 存储的形式化证明。
