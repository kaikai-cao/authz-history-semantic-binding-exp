# EXP-D3-02-04 — 历史完整性与撤销语义安全分析

**本轮最重要的一节。**
**前提**：推荐构造 A（`d3_02_circuit_spec.md`）能正确约束全部规则。以下分析从"电路无 bug"
出发，考察即使 `Verify(π) = 1` 仍然存在的攻击面。

---

## 0. 四个概念的严格分离

| 概念 | 定义 | 电路是否提供 | 提供者 |
| --- | --- | --- | --- |
| 历史**语义正确性** | 批次中每条事件满足 D3-01 的授权规则 | **是** | Halo2 电路 |
| 状态**承诺正确性** | `GR_next/RR_next` 是该批次作用于 `GR_prev/RR_prev` 的结果 | **是** | Halo2 电路 |
| 历史**完整性** | `E` 是授权服务真实、连续、未删改的事件序列 | **否** | D1-E 日志 + D2-B 锚定 + 可信批次来源 |
| 执行时**新鲜性** | 工具执行的那一刻，授权仍未被撤销 | **否** | 网关 fencing + D2-B freshness provider |

一句话：**电路把"语义正确"和"承诺正确"焊接成不可伪造的证明；它既不知道历史是否完整，
也不知道现在是什么时间。**

---

## 1. 历史完整性：五类攻击逐一构造

记真实历史 `H = (e_1, ..., e_n)`，证明者提交批次 `E`。
攻击者控制状态服务与证明者，但**不**能伪造 SHA-256/Poseidon 碰撞，**不**能改写带外
可信 checkpoint 中的 `C_prev` 与 `D_E`（若此假设失效，见 §1.6）。

### 1.1 删除某条撤销事件

- **攻击构造**：`H` 中 `e_j` 是 `Revoke(g, issuer)`。证明者提交 `E = H \ {e_j}`，
  用 `GR_prev` 之外的合法前状态（尚未撤销的版本）重算 `GR_next`，
  并把删减后的批次承诺 `D_E'` 交给可信来源签名。
- **电路能否发现**：**不能**。删掉 revoke 后的每条剩余事件仍然合法，
  `GR_next'` / `RR_next'` 与 `E'` 一致，电路给出接受证明。
- **防护**：`D_E` 必须来自**记录完整历史事件序列**的透明日志（D1-E 的 RFC6962 log），
  且日志的 STH / checkpoint 由 quorum 认证；网关核对 `D_E` 与 checkpoint 中的
  batch digest。若来源只对证明者提交的摘要签名，则攻击成功。
- **剩余风险**：日志本身若被 quorum 合谋绕过，或审计者不重放日志内容，仍可删撤销。
  这是外部信任，本轮不解决。

### 1.2 跳过中间授权事件

- **攻击构造**：`H` 中 `e_j` 是一个 grant。证明者提交 `E = H \ {e_j}`。
- **电路能否发现**：分两种：
  - 若 `e_j` 是后续 grant 的祖先 → parent 路径打开失败，电路**拒绝**（P04）；
  - 若 `e_j` 是旁支叶子，没有任何后续事件依赖它 → 电路**接受**，因为剩余事件合法，
    且 `GR_next'` 与 `E'` 自洽。
- **防护**：公开的 `GR_next/RR_next` 必须与网关从可信 checkpoint 取得的结果状态一致。
  删掉旁支 grant 会得到不同的 `GR_next`，被外部核对拒绝。
- **剩余风险**：如果验证者不核对结果状态（只验证 proof 有效），攻击成功。
  **"proof 有效"不是"状态正确"** —— 必须把公共输入与可信数据比对。

### 1.3 重放旧批次

- **攻击构造**：证明者拿到过去某批次 `E_old` 的有效证明 `π_old` 与公共输入，
  在当前直接重放。
- **电路能否发现**：**不能**。`C_prev` 与 `D_E` 都是旧值，但 circuit 只看它们是否自洽。
- **防护**：
  1. `previous_state_commitment` 必须等于网关当前可信 checkpoint 的 anchor（不是任意旧值）；
  2. `previous_epoch` 与本地 epoch 高水位比较（D2-B F01–F06）；
  3. 网关在工具执行时做 fencing（§2.4）。
- **剩余风险**：网关若不接受带外 checkpoint 或关闭 freshness provider，则无法防重放。

### 1.4 使用旧的合法状态

- **攻击构造**：证明者取旧但合法的 `S_old`，配一个从 `S_old` 出发合法的批次，
  生成完全有效的证明。
- **电路能否发现**：**不能**。电路只证明相对 `C_prev` 的转换，不知道 `C_prev` 的时间。
- **防护**：同 1.3。注意这与"授权规则正确"无关——状态本身是合法的，
  错的是**时间上下文**。这正是"epoch 单调 ≠ 新鲜"的具体体现。
- **剩余风险**：冷启动时没有本地高水位，必须完全依赖外部 freshness；provider 不可用
  时只能 fail-closed（D2-B 已实现此策略）。

### 1.5 合法但不完整的事件子集

- **攻击构造**：证明者取真实历史的一个连续子集 `H[a..b]`，配对应的前后状态，
  生成有效证明。这是"合法"的转换，但不是"从创世到当前"的完整历史。
- **电路能否发现**：**不能**，且**不应该**——本方案的语句本来就是单批次转换，
  不承诺覆盖全部历史。完整性由"批次序列"的外部链保证：
  - 递归方案 C 中，验证者核对最终 `C_n` 与 checkpoint；
  - 本方案 A 中，网关核对 `C_prev`（起点）与 `GR_next/RR_next`（终点）都来自可信数据。
- **防护结论**：验证者**不可**把"存在一个有效状态转换证明"解读为"这是全部历史"。
  文档与 API 必须显式标注该语句是**局部转换语句**，不是全局历史语句。

### 1.6 外部信任失效时的总体结论

若攻击者能改写 `C_prev` 或 `D_E`（即攻破 quorum / 日志 / 批次来源），
**上述五类攻击全部成功，电路无法补救**。因此本方案的完整性上界是：

> 在 D1-E 日志 append-only + quorum 认证 + 批次来源诚实的假设下，
> 电路保证被证明批次的语义正确与双根更新正确；它不增强这些外部假设本身。

这与 D3-01-R1 §10.5 的结论一致：规范性 Merkle 树只解决"相同状态集合的确定性承诺"，
不解决历史完整性。

## 2. 撤销新鲜性：证明有效 ≠ 授权现在有效

### 2.1 证明生成之后发生撤销

- 时刻 t1：证明 `π` 对状态 `S_t1` 有效，网关验证通过。
- 时刻 t2 > t1：issuer 撤销了相关 grant，`S_t2` 中该 grant 无效。
- `π` 仍然有效，因为它证明的是 t1 的转换，不是 t2 的授权状态。
- **结论**：证明必须带**短时效**，且网关在执行前必须重新取得当前状态承诺。

### 2.2 网关验证之后发生撤销（TOCTOU）

- 网关在 t1 验证 `π`，在 t2 才把工具调用发出；期间授权被撤销。
- 单纯"验证时检查"无法消除这个窗口。
- **必须**引入执行端的原子检查提交（§2.4）。

### 2.3 checkpoint 落后 / Witness Service 不可用 / quorum 未形成

| 场景 | 后果 | 要求的行为 |
| --- | --- | --- |
| checkpoint 落后于真实状态 | 可能把已撤销 grant 当作有效 | 用 epoch + hash 双字段判定（D2-B R1 已实现），拒绝旧 checkpoint |
| Witness Service 不可用 | 无法取得可信 `C_prev` | **fail-closed**：拒绝执行，不退化为"相信本地缓存" |
| 多见证者尚未形成最新 quorum | 只有部分签名 | 达不到阈值即拒绝；不得把部分 QC 当作认证（D2-B C01–C12） |
| 本地高水位存在但 checkpoint 更旧 | 回滚攻击 | 以 epoch 高水位拒绝（D2-B F01–F06） |
| 冷启动无高水位 | 无法识别旧状态 | 完全依赖外部 freshness；不可用则拒绝 |

**QC 只证明 quorum 认证，不证明最新性；freshness 是外部假设。** 这两句必须原样保留在
任何对外描述中。

### 2.4 执行端 fencing / 原子检查提交方案（至少一种）

推荐方案：**执行令牌 + 版本化 CAS（compare-and-swap）**

1. 网关在**工具调用即将发出时**，向授权状态服务请求一个短 TTL 令牌：
   ```
   token = Sig_quorum( agent_id, grant_id, resource, action,
                       epoch_current, GR_current, RR_current,
                       nonce, expires_at )
   ```
   `nonce` 一次性、`expires_at` 为数秒级。令牌对应的状态承诺必须是**当前** checkpoint 的值。
2. 网关把 `(token, decision_proof)` 一起交给执行端；执行端在**实际执行前**：
   - 校验 quorum 签名、TTL、nonce 未使用；
   - 对状态服务的版本计数器做原子 CAS：
     `CAS(version_seen_at_token, version_seen_at_execution)`；
     若期间发生任何 revoke（版本递增），CAS 失败，拒绝执行。
3. 撤销服务在写入 revoke 时**必须**递增同一个版本计数器，并使所有未过期令牌失效
   （或等价地让 CAS 失败）。
4. 执行成功后立即消费 nonce，防止同一令牌重放。

**这个方案的性质**：

- 它不试图让 Halo2 电路证明新鲜性；电路继续只证明历史语义。
-  fencing 的正确性依赖"撤销一定更新版本计数器"与"quorum 签名不可伪造"，
  这是**执行端**的外部假设，必须明写。
- 令牌绑定了 `agent/resource/action`，但它属于**决策层**，不是本轮状态转换语句的公共输入
  （见 `d3_02_public_statement.md` §3.6）。
- CAS 只能防"版本变化"，不能防"版本未变但语义改变"；后者由日志 append-only 保证。

备选方案（成本更高但更强）：在决策证明里把令牌作为公共输入，用 Halo2 同时验证 quorum
签名与 epoch 界限。本轮不做：Ed25519 在电路内代价高，且 D2-B 已在电路外实现验签。

## 3. ALLOW 与 DENY：本轮电路能证明什么

### 3.1 ALLOW（存在有效授权路径）

- 本轮的状态转换证明 π_trans **本身不证明 ALLOW**；它证明"批次语义合法且状态更新正确"。
- D2-A（冻结）证明的是 ALLOW：`∃ path: GR/RR 中某 grant 覆盖请求且未被撤销`。
- 组合后网关可以得到"在 `S_next` 下存在有效路径"的保证，前提是把 `GR_next/RR_next`
  作为 D2-A 的 public instance（已在 `d3_02_public_statement.md` §3.6 给出组合图）。
- **注意**：D2-A 已明确不验证 issuer 签名、不证明 DENY、不处理 freshness。

### 3.2 DENY（不存在任何有效授权路径）

**本轮电路不能证明 DENY。**

理由：

1. DENY 是**非存在性**语句：`∀ grant ∈ GR: 不覆盖该请求 ∨ 已撤销 ∨ 链路断开`。
   Halo2 电路是 NP 关系的证明，天然证明"存在 witness"；要证明"不存在"需要：
   - 枚举全部叶子（电路规模随状态爆炸），或
   - 一个承诺方案支持可验证的**非成员/全集穷尽**证明（本仓没有），或
   - 一个不同的语句：证明请求 resource 不在任何有效 grant 的前缀集合中。
2. 即使 `Verify(π_trans) = 1`，也只说明状态转换合法；它不排除某个未公开的 grant
   恰好覆盖请求。
3. 因此网关在拿不到有效 ALLOW 证明时，只能**fail-closed**（默认拒绝），
   不能把这个拒绝解释为"电路证明了不存在授权"。

### 3.3 明确声明

> 本轮设计**只能支持 ALLOW 类证明**（且需与 D2-A 组合）。
> 它**不是完整授权决策证明**，因为无法证明 DENY。
> 任何把"验证失败"等同于"授权不存在"的说法都是错误的。

## 4. 当前方案明确无法解决的攻击

| # | 攻击 / 场景 | 为什么无法解决 | 责任方 |
| --- | --- | --- | --- |
| U1 | quorum 合谋签署假 checkpoint | 电路不验签、不验证日志 append-only | D1-E / D2-B |
| U2 | 批次来源对删减后的事件签名 | 电路只信 `D_E`，不知道真实历史 | 透明日志 + 审计者 |
| U3 | 证明生成后 / 执行前发生撤销 | 电路无时间概念 | 执行端 fencing §2.4 |
| U4 | 网关不核对公共输入与可信数据 | proof 有效但对应错误状态 | 网关集成规约 |
| U5 | 通过 DENY 判定（不存在路径） | 非存在性语句，电路不支持 | fail-closed 策略 |
| U6 | 状态服务撒谎"规范槽位布局" | 电路只验证给出的槽位布局下的树重算 | 外部 witness 生成（已在规格 §2.8 明写） |
| U7 | D3 ↔ D2-A 域标签不一致导致的交叉误用 | 两个电路的 GR/RR 不是同一承诺 | 后续域对齐研究 |
| U8 | 资源前缀模型与生产系统不符 | 实验模型，不是生产授权语义 | 使用者自行约束 |
| U9 | 多授权来源 / 部分撤销 / 隐藏历史的组合 | 第一版只做 DirectOnly 单策略、小批次 | 未来构造 B/C |

## 5. 责任矩阵（交付时必须随文档一起给出）

```
授权事件产生       -> 授权服务（外部信任：事件真实发生）
事件写入日志       -> D1-E RFC6962 log（append-only + audit）
日志状态认证       -> D1-E checkpoint + 3-of-4 quorum + D2-B 验证器
批次承诺来源       -> 可信批次发布方（对完整事件字节计算 Poseidon 承诺）
语义与双根更新     -> Halo2 电路 π_trans（本设计的核心新增保证）
结果状态消费       -> 网关核对 GR_next/RR_next 与 checkpoint
授权路径存在性     -> D2-A 路径证明（ALLOW only）
执行时新鲜性       -> 执行令牌 + 版本 CAS（§2.4）
最终决策           -> 网关组合 + fail-closed（不产生 DENY 证明）
```

每一行的失败都**不能**由相邻行自动补偿。尤其：语义正确补偿不了历史不完整，
历史完整补偿不了执行时已撤销。
